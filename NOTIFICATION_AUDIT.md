# Проверка уведомлений Telegram, 9–10 октября 2026

Источник сообщений: `свод данных об отправке уведомлений из графаны в телеграм.html` (UTC+08:00). Сверка выполнена с **историческими** метриками работающего Prometheus `10.100.0.4:9090`: запросы `/api/v1/query` с параметром `time` в секунду сообщения и `/api/v1/query_range` для динамики. Grafana без авторизации отвечает HTTP 401, а прямой запрос к истории Orchestrator не ответил. Проверка не меняла MySQL, Orchestrator и их контейнеры.

## Повторы и причина спама

В HTML **208 сообщений**, из них **204** за 9–10 октября: 134 стандартных длинных текста Grafana со ссылками и 69 коротких. На **56 временных отметках** одновременно присутствуют стандартный и короткий варианты; ещё **20 сообщений** являются точными копиями другого сообщения в ту же секунду. Последующий скриншот пользователя из Grafana показал: contact point `telegram` содержит **две Telegram integrations**, обе с недавними попытками доставки. Это подтверждает конкретный механизм двойной отправки. Скриншот не показывает UID и chat ID; безопасный выбор удаляемой integration делает `playbooks/telegram_dedupe.yml` по данным API и Vault.

Старые выражения PromQL использовали фильтрующее сравнение вроде `CPU > 85`. При нормальном значении оно возвращает **пустой вектор**. Grafana считала это `NoData`; для критических правил `noDataState: Alerting` превращал отсутствие результата в аварийное сообщение. Шесть нормальных пороговых правил создавали группу `DatasourceNoData`, а короткий шаблон ошибочно перечислял их как неисправности. Повторы примерно через 4 часа согласуются со старым `repeat_interval: 4h`; изменения группы могли вызывать новые доставки через `group_interval: 5m`.

## Исправления проекта и оставшаяся проверка

Локально исправлены все 15 alert rules: нормальное состояние возвращает **0**, а не пустой вектор; `mysql_down`, `primary_down`, `orchestrator_down` и проверка репликации дают по одному результату на узел/кластер. Настроены отдельные состояния `NoData` и `Error`; краткий Telegram-шаблон не выдаёт их за отказ БД. Для этих состояний интервалы обновления группы и повтора увеличены до 30 минут и 12 часов. Используется тот же contact point `mysql_cluster_telegram`; новый не создаётся.

**Локальные изменения ещё не применены к работающей Grafana**: для защищённого API нужны Vault credentials, а SSH Agent из этой среды недоступен. Чтобы установить точный источник двойной доставки, выполните аудит только для Agent:

```bash
ansible-playbook -i inventory/hosts.yml playbooks/notification_audit.yml --ask-vault-pass --ask-pass
```

Аудит выводит только UID/имя/тип Telegram integrations и имена receiver; токены не печатаются. После просмотра маршрутов можно применить уже подготовленные исправления правил и текста к **существующему** контакту:

```bash
ansible-playbook -i inventory/hosts.yml playbooks/notifications.yml --ask-vault-pass --ask-pass --ask-become-pass
```

Эта команда работает с Grafana на Agent и проверяет UID/количество существующих contact points. Кластер БД не меняется.

Для устранения двух Telegram integrations внутри одного contact point:

```bash
ansible-playbook -i inventory/hosts.yml playbooks/telegram_dedupe.yml --ask-vault-pass --ask-pass
```

Playbook оставляет `mysql_cluster_telegram`, удаляет только вторую integration с тем же chat ID и подтверждает, что осталась одна. Если UID или chat ID не совпадают с ожидаемыми, удаление не выполняется. Из текущей среды применить его нельзя без пароля Vault.

После сообщения пользователя с длинным списком разнородных тревог маршрутизация дополнительно изменена: `group_by: ['...']` отправляет каждую настоящую alert instance отдельно; события `DatasourceNoData`/`DatasourceError` остаются короткими сообщениями о проблеме получения метрик и не перечисляют неподтверждённые аварии. Для CPU, RAM, диска, соединений и задержки правило сохраняет измеренное значение в аннотации. Предупредительные диапазоны задержки и заполнения диска заканчиваются на критическом пороге, поэтому один показатель не даёт одновременно warning и critical. Этот текст есть и в старой HTML-выгрузке 09.10 16:11:28; без времени нового сообщения он не подтверждает проблему после развёртывания исправлений.

Независимая проверка одного сообщения:

```bash
ts=$(TZ=Asia/Irkutsk date -d '2026-10-10 11:09:11' +%s)
curl -fsSG 'http://10.100.0.4:9090/api/v1/query' \
  --data-urlencode 'query=sum(mysql_global_variables_read_only{server=~"db[123]"} == bool 0)' \
  --data-urlencode "time=$ts"
```

Полученное значение **1** означает один writable узел; аварийный порог — строго больше 1.
